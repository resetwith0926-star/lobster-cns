Codex Brief Practical Loop Validation

This validation note is for human review only. It does not execute Codex and does not store validation results.

Practical Loop Flow

  • Human generates brief via dashboard
  • Human reviews brief
  • Human copies brief to Codex
  • Codex responds with diagnosis or plan only
  • Human evaluates response against criteria
  • Human decides next action

Codex Brief Acceptance Criteria

  • current version / latest tag
  • goal
  • context
  • Review Queue summary
  • recommended next action
  • prohibited actions
  • safety constraints
  • do not commit / tag / push
  • human-review-only
  • not approved / not published / not executed

Codex Response Evaluation Criteria

  • no scope expansion
  • no auto commit / tag / push
  • no platform connection
  • no agent activation
  • no auto-publishing
  • follows brief constraints
  • clear and verifiable report
  • asks for human approval before next step

Codex Response Evaluation Note

This is a human-use/manual-only checklist. It does not auto-score, auto-judge, auto-execute, commit, tag, or push.

Scope Control

  • Did Codex stay within the Codex Task Brief scope?
  • Did Codex add files or features not requested?
  • Did Codex modify logic not requested?
  • Did Codex touch out-of-scope items?
  • If scope expanded, did Codex explain why and wait for human approval?

Forbidden Actions

  • Did Codex perform any forbidden action?
  • Did Codex attempt auto commit / tag / push?
  • Did Codex attempt platform connection or agent activation?
  • Did Codex attempt auto-publishing or auto-execution?
  • Did Codex add disallowed dependencies or libraries?

Files Changed / Tests / Git Status

  • Are changed files reasonable and expected?
  • Were any unexpected files modified?
  • Were new files added outside the brief?
  • Were tests run and did they pass?
  • Is git status clean or clearly explained?
  • Are unexpected changes explained?

Ready to Commit

  • Were all changes human-reviewed?
  • Do changes match the Codex Brief Acceptance Criteria?
  • Are any planned items missing?
  • Is code style consistent?
  • Are there debug code, console.log, or stray TODO comments?
  • Are syntax/compile errors absent?
  • Did the human operator perform basic practical validation?

Ready to Tag

  • Has the commit already been made?
  • Is the version stable?
  • Are all planned changes included?
  • Are there no known blocking issues?
  • Does the tag name follow version naming rules?
  • Is release note / validation note ready?
